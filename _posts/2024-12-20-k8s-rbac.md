A new developer joins and needs to *read* Pods in the `dev` namespace, nothing more. Grant too much and a
mistake takes down production; grant too little and they file tickets all day. **RBAC** (role-based access
control) is how you draw that line precisely: a **Role** lists permissions, and a **RoleBinding** grants those
permissions to a subject.

### The four objects

Keep the pairing straight, it is the single most common RBAC confusion:

| Permissions object | Grant object | Scope |
|---|---|---|
| **Role** | **RoleBinding** | one namespace |
| **ClusterRole** | **ClusterRoleBinding** | whole cluster (and cluster-scoped resources like nodes) |

### A Role: what is allowed

A Role is a list of `rules`, each pairing API groups, resources, and verbs:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader
rules:
  - apiGroups: [""]              # "" is the core API group (pods, services, configmaps)
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
```

`apiGroups: [""]` is the core group; things like Deployments live in `["apps"]`. `verbs` are the allowed
actions, `get`, `list`, `watch`, `create`, `update`, `delete`.

### A RoleBinding: who gets it

The binding ties a subject (user, group, or service account) to a role via `roleRef`:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: dev
subjects:
  - kind: User
    name: dev-user
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

### Verify before you ship it

`kubectl auth can-i` answers a permission question **without performing the action**, and `--as` lets an admin
check access *as another user*:

```bash
kubectl auth can-i list pods --namespace dev --as dev-user      # yes
kubectl auth can-i delete pods --namespace dev --as dev-user    # no
kubectl auth can-i delete nodes --as dev-user                   # no (cluster-scoped)
```

### Gotchas

- `roleRef` is **immutable**, to point a binding at a different Role you delete and recreate it.
- Avoid `verbs: ["*"]` and `resources: ["*"]`; wildcards are how least-privilege quietly becomes
  most-privilege.
- A **Role** cannot grant access to cluster-scoped resources (like nodes); that needs a **ClusterRole**.

> kubectl get roles,rolebindings -n dev
